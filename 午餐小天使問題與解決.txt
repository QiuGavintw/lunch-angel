【第一章】LINE SDK v11 / Webhook 初期問題（問題 1）
==================================================

問題：

  專案初期建立 LINE Bot 時，遇到幾類典型問題：
  (a) LINE SDK v11 的 API 與常見舊版範例不同（client 取得方式、accessor 名稱）
  (b) Express body parsing 與 LINE signature verification 衝突
      ——簽章驗證需要「原始 raw body」，
      但 express.json() 解析後 req.body 已是物件，字串不同則簽章必失敗
  (c) webhook event（message / postback）如何分派、如何 replyMessage
  (d) 如何在沒有真實 LINE 流量的情況下測試 webhook 邏輯

使用者如何描述：

  初期以「照著 LINE Bot 範例建好，但簽章驗證 / 回覆出問題」的方向提出；
  確切的原始對話措辭目前資料無法確認。
  但結果留在 git history：commit a82289c 的主旨就是
  「fix: use correct sdk accessors and repair rich menu on skip」，
  直接證明「SDK accessor 用錯」是真實發生過、且被修正過的問題。

AI 分析：

  - 簽章驗證：@line/bot-sdk 的 middleware 以 raw body 計算 HMAC。
    解法是在 express.json() 加 verify callback，把原始 Buffer 存到
    req.rawBody（src/server.js:26-32 可證此結構存在）。
  - SDK v11：client 改由 LineBotClient.fromChannelAccessToken(...)
    取得（src/line/webhook.js:87、src/line/richMenu.js:28 可證），
    這正是 a82289c 修正後採用的 accessor 形式。
  - 簽章錯誤處理：SignatureValidationFailed → HTTP 401
    （src/server.js:59-61 可證）。
  - 測試：把 handleEvent / buildReplyText / buildQuickReply /
    isAppealMessage 等 export 出來，test/webhook.test.mjs 直接以
    mock event 呼叫，不需要真 token、不打 LINE API——
    這就是本專案的 test harness 模式。

嘗試過的方法 / 失敗原因：

  - 曾使用不正確的 v11 accessor（細節無法由 repository 重現，
    僅能由 a82289c 主旨與 diff 佐證曾經錯過一次並修正）。
  - 若不做 raw body 保存，express.json() 重新序列化的字串與 LINE 原始
    payload 不一致，簽章必然驗證失敗（機理性問題，非猜測）。

最終解決方式：

  1. express.json({ verify: (req,res,buf) => { req.rawBody = buf; } })
  2. @line/bot-sdk middleware({ channelSecret }) 作為 /webhook 前置驗證
  3. SignatureValidationFailed → 401
  4. handleEvent(event) 統一處理 event 分派，replyToken 缺失直接 return null
  5. export 核心函式供 node:test 測試（mock harness）

驗證方式與結果：

  - test/webhook.test.mjs（現有 12 個 test）涵蓋：
    keywords、postback（today/tomorrow/week/date/info/about）、
    date query、quick reply、未知 postback 等。
  - 目前整包 npm test 35/35 PASS（parse 12 + service 11 + webhook 12；
    test 數量由三個測試檔逐一統計得證；
    35/35 PASS 為維運紀錄中最近一次執行結果）。

相關 Commit：

  a82289c — fix: use correct sdk accessors and repair rich menu on skip（2026-08-11）
  （rawBody / 401 結構屬於初始 commit 813daac 既有的設計）

Deploy 狀態：

  813daac 即以「prepare for deployment」為名提交；實際 Render 部署時間點
  目前資料無法確認（部署由使用者手動於 Render Dashboard 操作，
  repository 不留部署紀錄）。

最後結果：

  Webhook 簽章驗證、event 處理、replyMessage、mock 測試全部穩定運作，
  成為之後所有功能的基礎。

【第二章】官方資料取得與 PDF 解析（問題 2）
==================================================

問題：

  午餐菜單不是結構化 API，而是學校官網公告文章裡附的 PDF 檔，
  而且是「表格型」PDF：日期欄位在表頭，每天一格直欄，
  內含主食／主菜／副菜1~4／點心／過敏原等多列。
  要把這種 PDF 變成「2026-06-15 吃什麼」的 JSON，不能只靠文字搜尋。

使用者如何描述：

  需求方向為「自動從馬公高中官網抓午餐、解析 PDF 菜單、存起來給 bot 查」；
  原始對話措辭目前資料無法確認，但整條 pipeline 已完整存在於 code。

AI 分析——為什麼不能只靠單純的文字搜尋：

  這是本章最重要的設計判斷。理由如下：
  1. pdf.js getTextContent() 吐出的是「一堆帶座標的文字 token」，
     不是有列欄概念的表格。純文字串接後，「6」「/」「15」可能被拆成
     多個 token，菜色也會交錯，無法知道哪道菜屬於哪一天。
  2. 因此 pdf.js 的做法是「座標驅動」而非「文字搜尋驅動」：
     - clusterLines()：以 y 座標（epsilon 2.2px）把 token 聚成視覺行
     - findDateLine()：找到「日期 6/15 …」那一天的表頭行
     - parseDateColumns()：從表頭行解析出每個日期欄的 x 中心點
     - buildColumnTokens()：所有 y < dateY 的 token 依 x 中心點分配到
       所屬日期欄（容差 COL_TOLLERANCE=55、合併 MERGE_GAP=70）
     - extractAdYear()：抓「115年」並轉西元（+1911）
     - findAllergenY()：定位過敏原列，避免把過敏原符號誤當菜名
     （以上皆可在 src/lunch/pdf.js 直接讀到）
  3. 就算解析成功，也不能直接相信：validator.js validateRecord()
     逐日驗證欄位合理性；sync.js integrityCheck() 再以
     「日期範圍天數 vs 實際解析天數」的覆蓋率做整份文件完整性檢查
     （例如 span>=4 天但只解析出 <35% → 判為異常，sync.js:273-294 可證）。

最終架構（sync pipeline，src/lunch/sync.js 可證）：

  RSS 抓取（rss.js fetchLunchFeed）
    → 過濾 title 含「菜單」的公告
    → menuPdfUrl() 找出公告內官方網域的 PDF URL
       （OFFICIAL_HOSTS 白名單：www.mksh.phc.edu.tw / mksh.phc.edu.tw）
    → downloadPdf()：15 秒 timeout、Content-Type 檢查、
       前 5 bytes 必須是 '%PDF-' magic check
    → parseMenuPdf()（pdf.js）→ buildEntriesFromPdf()（parse.js）
    → validateRecord() 逐日驗證 → integrityCheck() 整份驗證
    → merge 進 cache → safeWriteJson() 原子寫入 data/lunch.json
  若公告沒有 PDF → fallback 到純文字 buildEntryFromText()

  另外有一個明確的防呆設計 ParserUnsupportedError：
  解析出 0 天時丟 BLOCKER，reportBlocker() 印出
  「先抓取此 PDF 檢查新版格式，再擴充 parser，勿猜測。」
  ——這句話正是後來 2026-08-21 新格式事件的指導原則（見第十章）。

驗證方式與結果：

  - test/parse.test.mjs 以真實官方 PDF（June 格式）跑 parseMenuPdf，
    驗證 10 天、四副菜、dessert 保留等（現有 12 個 test）。
  - data/lunch.json（git 追蹤）實際含 2026-05-29 ~ 2026-08-11 資料，
    證明 pipeline 端到端成功過。

相關 Commit：

  813daac — 建立 rss/sync/pdf/parse/validator 全套
  882fdd4 — fix: support four lunch sides and improve pdf parsing（2026-08-12）
             （副菜支援 1→4 道、safeDish、integrityCheck、+282 行測試）

Deploy 狀態：

  已隨各階段部署至 production（手動部署；確切時間無法由 repository 確認）。

最後結果：

  官網 → PDF → 結構化 JSON 的完整 pipeline 穩定運作，
  並且具備「解析失敗就整份擋下、絕不覆蓋舊資料」的安全特性。

【第三章】每日同步、scheduler 與 cache 保護（問題 3）
==================================================

問題：

  官方網站隨時可能更新菜單；bot 又必須秒回查詢。
  如何兼顧「每日自動同步」與「絕不讓錯誤資料覆蓋既有正確資料」？

AI 分析與最終設計（全部可由 code 證實）：

  1. scheduler（src/lunch/scheduler.js）：
     - 每日 05:00 Asia/Taipei 觸發。
       不是固定 setInterval(24h)，而是 nextRunDelayMs() 用 Intl timezone
       換算到下一個 05:00 的精確延遲，不受 Server 本機時區影響。
     - 失敗重試 MAX_ATTEMPTS=3 次，BACKOFF_MS=3000ms，
       且單次失敗不會停止 scheduler，隔日照排（fire → scheduleNext）。
  2. startup sync：
     startLunchScheduler() 時若 meta.lastSuccessDate != 今天（Asia/Taipei），
     先跑一次非強制同步（runStartupIfTodayPending）。
     並刻意設計為非 await 的 background task：webhook readiness 不等它完成。
  3. 同步鎖（data/lunch-sync.lock，gitignored）：
     flag: 'wx' 建立 lock；EEXIST 時檢查 lock owner pid 是否存活
     （process.kill(pid,0)；ESRCH → stale → 安全移除重建；
      Windows／權限等無法確認的情況採 fail-safe：視為仍在執行、不刪 lock）。
  4. cache 更新保護（多層防線）：
     a. 任何一步失敗（RSS 抓取失敗 / RSS 空 / 找不到菜單公告 /
        下載失敗 / parser 解析 0 天 / validation 失敗 / integrityCheck 失敗）
        → failSync()，data/lunch.json 完全不被碰觸
        （sync.js 各分支 console.error 明寫「已保留現有 data/lunch.json」）。
     b. integrityCheck 覆蓋率異常或 ParserUnsupportedError
        → 標記 BLOCKER，break 掉整輪，「保留全部舊資料，不做 partial update」。
     c. 寫入本身是原子操作 safeWriteJson()：先寫 ${file}.tmp 再 rename，
        期間任何失敗都不會破壞現有資料。
     d. merge 語法只覆蓋「本份文件解析出的日期」，
        其他既有日期原封不動保留（sync.js:473-480 可證）。
     e. metadata（data/official-sync.json，gitignored）記錄
        lastDocumentId / lastDocumentHash；同一份文件未變就 skip，
        不重複抓取與覆蓋。
  5. DATA_DIR 環境變數：
     未設定 → 用專案內 data/（本機開發不變）；
     有設定（如 Render Persistent Disk 掛載路徑）→ 使用該路徑。
     ——這個機制當時就已做好，但 production 實際上沒有掛 Persistent Disk，
     後來因此踩到 ephemeral storage 問題（見第十二章）。

驗證方式與結果：

  - sync 內建 FORCE_PDF_FAIL / FORCE_VALIDATE_FAIL / FORCE_RSS_FAIL
    三個測試 hook（正常執行不觸發），可用於演練各種失敗路徑。
  - data/lunch-sync.lock 實際存在於本機 data/，lock 機制實際運作過。

相關 Commit：

  813daac — scheduler/sync/cache 全套建立
  74d9ac7 — feat: hide regular weekends from weekly lunch menu（2026-08-11）
            （本週菜單忽略無特殊供餐的一般週末；補課/補假/國定假日/
              校慶/特殊供餐提示的週末仍顯示）

Deploy 狀態：

  已部署（手動）；production scheduler 於 Render log 可見
  （來自維運紀錄：build PASS / health PASS / scheduler PASS / startup sync PASS）。

最後結果：

  每天 05:00 Asia/Taipei 自動同步 + 失敗重試 + 多層 cache 保護，
  至今沒有發生過「壞資料覆蓋好資料」事故。

【第七章】Phase 10D — 冷啟動首次無回覆診斷（2026-08-12）
==================================================

問題（使用者觀察到的現象）：

  Render 冷啟動（瀏覽器久沒開／容器剛醒）後，
  第一次從 Rich Menu 點擊常常沒有任何回覆；
  webhook log 也沒有立即出現 event arrival；
  等一段時間再點才成功（某次約數分鐘後才見 arrival，
  另一次重啟後約 35 秒成功）。以上為維運紀錄。

使用者如何描述：

  「為什麼第一次點都不會回，等一下再點就好了？」的方向。

AI 分析（嚴格區分事實與推論——沿用既有紀錄的方法論）：

  已確認的事實（repository 可證）：
  1. registerWebhook(app) 在 app.listen() 之前呼叫 → 沒有 route 註冊 race。
  2. startLunchScheduler() 在 listen callback 才啟動。
  3. startup sync 是非 await 的 background task，不阻塞 listen。
  4. （當時）/health 在 listen 後立即回 200，沒有 ready flag。
  5. 當時 pdf.js 在 module 頂層 static import pdfjs-dist，
     所以 scheduler → sync → pdf.js 形成一條 eager import chain，
     冷啟動時要一起載入。
  6. getTextContent() 是 CPU-bound 的同步大量計算。

  強烈推論（非直接量測）：
  - eager import chain 是冷啟動成本之一。
  - PDF 解析可能短暫佔住 event loop，使同時刻抵達的 webhook 延遲。

  無法由 repository 驗證（僅維運量測紀錄）：
  - fresh process import 時間數字（express 約 540ms、@line/bot-sdk 約 596ms、
    scheduler→sync 約 640ms、總計約 1.86 秒）。
  - Render Free container 對啟動期間抵達 request 的處理方式
    （queue / drop / retry 屬平台層機制，無法從 code 證明）。

嘗試過的方法：

  先加觀測、再談修復——Commit 2f4ed74
  「feat: add webhook diagnostic logging」（webhook.js +45 行）：
  logEventArrival / logReplyOutcome / logLineReplyError 三組日誌，
  讓每次 event 抵達、reply 成敗、LINE API 錯誤都有跡可循。

失敗原因（當下的限制）：

  只加 logging 當然不會讓冷啟動變快；它的價值是「定位問題」，不是解藥。
  真正的結構性改善放在 Phase 10E（下一章）。

相關 Commit：

  2f4ed74 — feat: add webhook diagnostic logging

最後結果：

  觀測到位後，確定了改善方向：
  (a) readiness 要誠實（/health 不能在 bootstrap 前就回 200）
  (b) 重模組要 lazy load。兩者都在 10E 落實。

【第八章】Phase 10E — Readiness + Lazy PDF Import（問題 4）
==================================================

問題：

  /health 在 Node 還沒完成 bootstrap 時就可能回 200，
  health status 無法真正代表 application readiness；
  加上 pdfjs-dist 被 eager import，冷啟動成本高。

AI 分析：

  Render 的 Health Check 打 /health；
  如果 /health 太早回 200，平台會以為服務好了，
  但此時 webhook handler 可能還在載入依賴 → 使用者第一次點擊無回覆。
  另外 pdfjs-dist 只在 sync 時需要，不需要在 server 啟動時就載入。

修改內容：

  src/server.js：
  1. let ready = false
  2. listen callback 內 markReady() 才轉 true（listen 之後才算 ready）
  3. /health：ready=false → 503 {"status":"starting"}；
     ready=true → 200 {"status":"ok","ready":true}
  4. STARTUP_T0 / startupElapsedMs() startup timing logs：
     [startup] static imports completed / server listen ready (+Xms) /
     application ready (+Xms) / lunch scheduler started (+Xms)
  5. LUNCHANGEL_STARTUP_READY_DELAY_MS 測試 hook（預設 0，
     生產路徑完全不受影響；>0 時用 setTimeout 模擬慢 bootstrap，
     用來驗證 503→200 行為）

  src/lunch/pdf.js：
  6. pdfjs-dist 從 module 頂層 static import 改為 parseMenuPdf()
     函式內 const { getDocument } = await import('pdfjs-dist/...')
     ——scheduler/sync 的冷啟動 import chain 從此不含 pdfjs。

  架構原則（重要）：
  7. lunch sync 不是 webhook readiness 的 prerequisite。
     server ready 即可接 webhook；background sync 慢慢跑。

為什麼需要這些修改（一句話版）：

  讓「健康檢查通過」與「真的能處理 webhook」畫上等號，
  並把最重的依賴移出啟動路徑。

如何驗證 regression：

  - /health pre-ready 503 PASS、ready 後 200 PASS、
    unsigned webhook 401 PASS、payload regression PASS
    （session 手動驗證紀錄；test/ 沒有 server 測試檔，
     這些無法由 repository 重現，如實標註）。
  - real PDF parsing PASS：npm test 中 parse/service 測試全數通過
    （lazy import 後 parser 功能不變）。
  - lazy scheduler import chain 約 200ms → 24~27ms
    （❌ 無法由 repository 驗證：無基準測試程式，屬 session 量測）。
  - 目前整包 35/35 PASS（含後續新增測試）。

限制（誠實面）：

  Render container 在 Node 啟動之前的 cold start 屬平台層，
  這些程式碼不可能完全消除；PDF getTextContent() 的短暫 CPU blocking 仍在。
  10E 的目標是 Node application readiness，不是宣稱消滅 cold start。

相關 Commit / Deploy 狀態（重要細節）：

  - 當下（10F 期間）server.js 與 pdf.js 都是 working-tree 未 commit 變更。
  - pdf.js 的 lazy import 後來隨 bcbf6ed（2026-08-21）進入 git；
    server.js 的 ready flag 至今仍未 commit。
  - production 實際跑的是包含 10E 行為的版本
    （Render log 出現 [startup] timing logs，屬維運紀錄），
    但若只看 git HEAD 會看不到 ready flag——這是已知差異點，
    未來應補 commit（不在本次任務範圍）。

【第十二章】2026-08-21 — 新午餐菜單 PDF 解析成 0 天（問題 12）
==================================================

這是本專案最重要的一次 parser 事件。

問題（實際 log）：

  sync log 出現：
    行政1150831~0904菜單 → OK (0 天)
  但同一時間舊格式文件：
    行政115年6月15日~29日午餐菜單
  仍然可以解析成 10 天。

  「OK (0 天)」代表公告被抓到了、但 parser 一天都沒解析出來
  ——照設計會觸發 ParserUnsupportedError BLOCKER，保住舊 cache，
  但新菜單（開學週！）就是進不了系統。

使用者如何描述：

  回報「新的菜單沒有進來／查不到下學期的午餐」，並提供上述 log 方向。

AI 分析——如何找到真正原因（兩層原因，缺一不可）：

  第一層：routing 失敗——PDF 根本沒進 parser？
  追查 menuPdfUrl()（sync.js）：原本要求 PDF URL decode 後必須包含
  「午餐菜單」四個字。
  舊 PDF URL：
    ...115年6月15日29日午餐菜單-公告.pdf   ← 含「午餐菜單」✓
  新 PDF URL：
    .../11508310904-菜單公告.pdf          ← 只有「菜單」，沒有「午餐菜單」✗
  → menuPdfUrl() 回 null → 走不到 downloadPdf/parseMenuPdf。
  （證據：bcbf6ed diff 中 sync.js 把 '午餐菜單' 改成 '菜單'）

  第二層：日期 token 格式不同——就算 routing 通了也解析不出來。
  pdf.js parseDateColumns() 原本假設表頭 token 是拆開的：
    舊：'6' '/' '15'（月份 token、斜線 token、日期 token 分開）
  新 PDF 的 getTextContent() 卻吐出合併 token：
    新：'8/31'（月/日合在同一個 token）
  → 原本的 monthMatch/slashMatch 序列匹配不到任何欄位 → 0 欄 → 0 天。
  （證據：bcbf6ed diff 中 parseDateColumns 整段重寫，
    測試 Case B 直接以真實新 PDF URL 驗證）

診斷方法論（值得記下來）：

  - 遵循 reportBlocker() 的既定原則「先抓取此 PDF 檢查新版格式，
    再擴充 parser，勿猜測」——直接抓真實新 PDF 看 token 結構，
    而不是憑空猜 parser 哪裡壞了。
  - 「同一份 code 舊格式 OK、新格式 0 天」這個對照組，
    把問題範圍收斂到「新格式的差異點」，而不是全面懷疑。

最終解決方式（commit bcbf6ed，diff 可證）：

  1. sync.js menuPdfUrl()：比對字串由「午餐菜單」放寬為通用的「菜單」
     （decode 失敗時 fallback 用原始 URL 比對，此保護原本就有）
  2. pdf.js parseDateColumns() 重寫支援三種形態：
        8/31    （完整 token：月/日）
        8/+31   （斜線黏在日token前）
        8+/+15  （月與斜線/日分離的多 token 組合）
     邏輯：/^(\d{1,2})\/(\d{1,2})?$/ 抓完整 token；
           否則純數字月 token + 下一 token /^(\/+)(\d{1,2})?$/；
           再從後續純數字 token 補齊不足兩位的 day。
  3. 增加合理範圍驗證：month 1–12、day 1–31，
     超出直接跳過（防止把非日期數字誤判成日期欄）。
  4. 順帶把 10E 的 pdf.js lazy import 一起帶進這個 commit
     （parseMenuPdf 內 await import('pdfjs-dist/...')）。

【第十五章】Render ephemeral storage 導致舊資料消失（問題 15）
==================================================

問題：

  10G-2 部署成功後，發現 2026-06-15 等六月舊資料在 production 可能查不到。

第一時間容易誤判的方向（刻意記錄下來）：

  「是不是 parser 改壞了，舊 PDF 現在解析不出來？」

AI 分析——把兩件事分開看（這是本章核心）：

  1. 程式解析能力（parser capability）：
     Phase 10G-1 的 Case A regression test 已經證明：
     舊 PDF 仍然解析得出 10 天（35/35 PASS）。
     → parser 沒有壞。
  2. production cache persistence（資料持久性）：
     真正原因是部署環境問題：
     - production 沒有設定 DATA_DIR
     - Render 沒有掛 Persistent Disk
     - 因此 production 使用專案內 data/
     - 而 Render 的 filesystem 是 ephemeral（短暫的）
     → 每次 redeploy，容器重建，舊 cache 檔案直接消失
     → 新容器的 startup sync 只會重新抓「目前官方最新的菜單」
       （pickTargets 只挑最新一份文件）
     → 所以 cache 只剩 8/31~9/11，六月的資料不是「解析失敗」，
       而是「部署後 cache 根本不存在」。

判斷順序（方法論）：

  先用 regression test 排除程式問題 → 再往環境層找原因。
  如果反過來先去改 parser，就會白改而且引入風險。

當下的狀態與後續方向：

  - README.md 其實早已寫明：
    「Persistent Disk：需要。……否則午餐 Cache 會遺失」
    以及 DATA_DIR 應指向 Persistent Disk 掛載路徑——
    也就是說，這個風險在文件上是已知項，但 production 環境尚未配置。
  - 短期影響：舊日期查詢回 📭 空資料（formatEmptyDateMessage，
    屬既有正常行為）；當期菜單查詢完全正常。
  - 根本解法（掛 Persistent Disk + 設定 DATA_DIR）屬 Render Dashboard
    操作與未來任務，本次歷史整理不予執行。
  - 另一個可考慮的方向（僅列出，未實作）：cache 由 git 追蹤的
    data/lunch.json 在 repo 中保有 5/29~8/11 的資料，
    未來若需要可在啟動時 seed——目前資料無法確認此方案是否已被討論採納。

【第十四章】Phase 10G-3 — 菜單異動公告自動套用（課題 15）
==================================================

◆ 緣由
　官方除了發布正式菜單 PDF 之外，也可能發布「菜單異動／更正公告」（例如
　2026-08「行政8/31~9/11菜單異動」），內容為一行一天、以「M/D」開頭、描述
　當日菜色的 增／刪／替換／選擇規則。先前 sync 只處理正式菜單 PDF，異動公告
　內文未套用，導致 LINE 回答的菜色與官方當日公告不一致（例如 8/31 主菜實際
　為「冬瓜排骨」單一主菜，PDF 仍為「冬瓜排骨 / 黑椒雞丁 (擇一)」）。

◆ 觀察
　1. 異動公告的內容在 feed 中是包在 CDATA 的 HTML（<p>/<br>），沒有實體
　　 換行；直接用 split('\n') 解析不到任何日期行。
　2. feed 中同一篇公告的內文會被重複出現很多次（6/8~6/29 一篇甚至重複
　　 30 次以上）；若不處理，規則向量會膨脹數十倍、needsReview 與日誌爆量。
　3. 歷史異動公告（5/29~6/5、6/8~6/29 等）與「當期正式菜單」日期完全沒有
　　 交集；若全數套用，會產生數千筆對不上日期的 needsReview（浪費記憶體、
　　 製造大量無效 log）。
　4. 公告格式前後不一：
　　 - 當期 8/31~9/11：改為／更改為／取消／新增／本日主菜僅一種／沒有2選1
　　 - 歷史 6/8~6/29：更改為／更改／改／取消／新增／主菜雙拼(3選2)／2選1
　　 - 歷史 5/29~6/5：整列菜單為菜名清單、用「增加」而非「新增」、
　　   也有「滷豆干改滷豆腐」的「改」式。
　5. 蔬菜替換（9/7青江菜、9/8小白菜、9/9空心菜、9/10A菜、9/11莧菜）
　　 在正式菜單欄位中並不存在（PDF 只寫「季時蔬菜」）——不能亂塞。
　6. 9/2 新增鮮肉包當日 main/side1~side4 已全滿，沒有可安全放置的欄位。

◆ 根因
　1. 舊流程只解析 PDF，沒有「異動公告」這條資料來源。
　2. 對 HTML/CDATA 內容直接逐行 parse → 一行都對不上。
　3. 沒有「日期範圍重疊」或「規則去重」的保護 →
　　 歷史公告重複內文全部掃進來，報表與記憶體爆量。

◆ 解決方案（src/lunch/corrections.js）
　1. toPlainLines()：剝離 CDATA、<br>/</p> → 換行、去標籤、解 &nbsp;/&amp; 等，
　　 把單行 HTML 還原成「一行一天」的純文字。
　2. parseCorrectionLines()：只吃「M/D 開頭」的行；「M/D~M/D 異動如下」
　　 標題行跳過；以「，／，」切小句，逐句分類：
　　   取消（A取消、A、B取消）→ 替換（更改為 > 更改 > 改為 > 改成 > 改）
　　   → 新增（新增/增加）→ 主菜僅一種／沒有2選1 → 其餘記為 note。
　　 「X改為Y、Z取消」的混合句先偵測「、」前段含「改」再拆段，避免
　　 把「滷甜不辣改水煮蛋」誤當成取消清單。
　3. applyCorrections()：深拷貝 base records 後逐日套用；找不到菜名欄位
　　 一律 needsReview（不猜測、不改動）；新增菜色優先放 main，其次
　　 第一個空格 side1~side4，全滿則 needsReview（如 9/2 鮮肉包）。
　　 重複 token（如替換造成「A / A」）與同欄重複菜名會去重。
　4. applyCorrectionsFromPosts()：套完後逐日重新 validateRecord，任一
　　 天驗證失敗就「回退正式菜單原值」並記入 reverted（不覆蓋正確資料）。
　5. 去重與範圍保護：
　　 - extractCorrectionRules 只採用「與 base 日期重疊」的公告
　　   （postOverlapsDates），歷史公告自然被排除（對應 9 月菜單，6/8~6/29
　　   公告無交集 → 0 條規則）。
　　 - 規則以 dateRaw+內容 signature 去重，杜絕內文重複造成的膨脹。
　6. sync.js 整合：在 PDF 解析 → invalid 檢查之後、寫入 cache 之前，
　　 in-memory 套用異動，再執行 validation passed → merge → atomic write。
　　 異動公告由 isCorrectionPost()（標題含異動/加菜/變更/更正 + 內容有
　　 M/D 與增刪改字樣）識別；正式菜單與異動各自處理，互不干擾。

◆ 套用結果（本次 8/31~9/11）
　- 8/31 main：冬瓜排骨（單一主菜）　　9/1 main：香滷肉燥
　- 9/3 main：醬汁里肌肉片 / 滷雞腿 (擇一)　9/4 main：洋蔥肉絲 / 炸雞翅 (擇一)
　- 9/7 main：花生燒雞（取消糖醋排骨、滷雞腿後新增，單一主菜）
　- 9/9 main：梅干雞丁 / 紅燒鱸魚 (擇一)　　9/11 main：滷骨腿
　- 9/2 披薩口味、披薩飯2擇1 → note；新增鮮肉包 → needsReview（無欄位可放）
　- 青江菜/小白菜/空心菜/A菜/莧菜 五項替換 → needsReview（欄位中無對應菜名）
　- applied 11 條、needsReview 6 條、note 3 條；套用後逐日 validateRecord 全數通過。
　- 重複執行（相同 base + 相同規則）結果一致（idempotent）；cache 寫入
　　 以臨時 DATA_DIR 驗證，production data/ 未動。

◆ 測試（test/corrections.test.mjs，新增 15 案，全部 PASS）
　- toPlainLines（CDATA/HTML/Br）／真實 8/31~9/11 公告解析（21 條規則）
　- Case C 逐項替換、Case D 取消+新增、Case E 主菜僅一種、
　  Case F 9/2 複合異動（note + 鮮肉包 needsReview）
　- 蔬菜替換 needsReview 誠實性、idempotent、重複規則去重
　- June 公告與 9 月菜單無交集 → 不套用
　- Case G 歷史公告（6/8~6/29、5/29~6/5）可延伸解析、不崩潰
　- applyCorrectionsFromPosts 端到端（真實 PDF base + 真實公告）＋驗證失敗回退
　- isCorrectionPost 識別
　- 全量 npm test：54/54 PASS（原 35 + 新增 19：corrections 15 案 + service 4 案）。

◆ 注意事項
　1. 異動公告只在「日期與正式菜單重疊」時套用；換新菜單週期請留意
　　 新公告的日期範圍自動被納入（resolveDate 依 base 日期解析年份）。
　2. 公告日期在 base 之外 → needsReview（conservative，不猜測）。
　3. 蔬菜替換目標是通稱「季時蔬菜」時無法對位 → 刻意保留 needsReview，
　　 由人工在後續公告確認，避免誤改。
　4. 本階段未 commit／push／deploy（依課題規範）。

Phase 10G-3 補充｜依需求書第 20 節格式
--------------------------------------------------

【使用者需求】
　馬公高中網站會另外發布午餐菜單勘誤／異動公告。LINE 目前只抓原始 PDF，
　造成後續菜單修改沒有同步。使用者要求爬取官方異動公告並更新 LINE。

【問題】
　原本 lunch sync 只處理原始菜單 PDF。官方異動是另一篇公告；不同歷史公告
　格式不一致（改為／更改為／改／取消／新增／增加／主菜雙拼／2選1／整列菜名）。
　有 replace / add / cancel / 主菜選擇規則等不同語意，不能靠單一 hardcode 或
　單一 regex 解決。

【調查】
　RSS 已可抓到「行政8/31~9/11菜單異動」，並列出完整官方異動規則（22 節下方
　Before/After）。也調查到歷史公告「行政6/8~6/29午餐加菜、變更公告」、
　「行政5月29日~6月5日更改菜單(詳內文)」；確認歷史格式比目前公告更多樣
　（6/8~6/29 一篇在 feed 中內文重複 30 次以上；5/29~6/5 用「增加」且含整列
　菜名行）。另確認 8/31~9/11 正式 PDF 的「季時蔬菜」無法對位公告中的
　青江菜／小白菜／空心菜／A菜／莧菜替換 → 這些目標在 base 中不存在。

【解法】
　建立（src/lunch/corrections.js）：
　 - Errata detector：isCorrectionPost（標題含異動/變更/更改/勘誤/加菜/更正 +
　   內容有 M/D 開頭與增刪改字樣），不 hardcode URL／文章 ID／完整標題。
　 - Errata parser：parseCorrectionLines（一行一天、以「，／，」切小句），
	   支援 改為/更改為/更改/改成/改 → replace；新增/增加 → add；
	   取消（A、B取消）→ remove；本日主菜僅一種/沒有2選1 → single-main；
	   其餘 → note；「X改為Y、Z取消」混合句拆段處理。
	 - 過濾：YouTube URL、※備註、括號說明不得污染菜名。
	 - Correction applier：applyCorrections／applyCorrectionsFromPosts。
	   依日期套用 → locateDish 找到包含菜名的欄位才改 → 0 個或 >1 個匹配一律
	   needsReview（不猜測、不改動）→ 找不到資料欄位一樣 needsReview。
	   新增菜色優先 main，其次第一個空 side1~side4，全滿 → needsReview。
	 - 多主菜收斂：collapseMainToSingle（去重／去(擇一)），8/31 與 9/7
	   最後為「單一主菜」，不再殘留 糖醋排骨/滷雞腿/擇一/2選1。
	 - 去重與範圍保護：extractCorrectionRules 只採用「與 base 日期重疊」的
	   公告（postOverlapsDates），並以 dateRaw+內容 signature 去重，
	   歷史六月公告對九月菜單無交集 → 0 條規則。
	 - Idempotent：相同 base + 相同規則 → 相同結果；重複內文不重複套用。
	 - Sync 整合：PDF 解析 → invalid 檢查 → applyCorrectionsFromPosts →
	   逐日 validateRecord（任一失敗回退正式菜單原值，記 reverted）→
	   validation passed → merge → atomic write。LINE 讀取 corrected cache。
	 - 9/2 特殊案例：schema（main/staple/side1~4/dessert + info）無法精確表達
	   三層資訊（披薩/飯2擇1 × 披薩內兩口味擇一 × 每人一片）。為避免誤導，
	   不把兩種口味塞進 main（不偽造雙主菜）；口味與「披薩、飯2擇1」記為
	   note（sync log），主菜欄位維持「披薩」、主食維持飯類 → LINE 顯示
	   不誤導（見 service.test 9/2 案）。鮮肉包（當日副菜全滿）→ needsReview。
